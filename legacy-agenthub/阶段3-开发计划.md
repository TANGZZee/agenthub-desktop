## 0. 阅读须知

### 0.1 本阶段做什么、不做什么

| | 内容 |
|---|---|
| **阶段3 要做** | 让 Hermes 真正拆任务（当 Supervisor）；让 Sidecar 真正按任务调度；把 Pi / Claude Code / Codex 三个 Worker **加上 Hermes（仅作为规划器）** 从"占位配置"换成**真实可运行**的适配器；建立成本与用量记录；建立失败重试、换 Agent、升级给用户的规则；建立手动改派与紧急停止；在前端做出"任务时间线" |
| **阶段3 不做** | 共享 Skills 的同步与格式转换（阶段4）、Git Worktree 隔离（阶段5）、打包与安装（阶段6） |
| **阶段3 的硬边界** | 不允许多个 Agent **并行修改同一批文件**。阶段3 只允许"并行只读任务"和"串行写任务"，真正的并行隔离留给阶段5 |

### 0.2 术语表（通俗版）

| 术语 | 一句话解释 |
|---|---|
| **Supervisor（Hermes）** | 大管家。听懂你的目标，把它拆成几条子任务，决定每条派给谁。**它只负责"提案"，不负责"批准"**（见 §2.3） |
| **Worker** | 真正干活的执行 Agent：**Pi、Claude Code、Codex**（Hermes 是 Supervisor，不是 Worker） |
| **Sidecar** | 监工。它管进程、管钱、管文件冲突、管审计。**大管家的提案要过它这一关** |
| **TaskEnvelope（任务信封）** | 一条子任务的标准表格。写清楚：谁做、做什么、用什么档次、能碰哪些文件、怎么算做完、花多少钱就得停 |
| **AgentCapability（能力登记）** | 每个 Agent 的"履历表"。写清楚：它到底会什么、装没装、跑不跑得起来 |
| **Adapter（适配器）** | 翻译官。四个 Agent 的命令行参数、输出格式都不一样，适配器把它们统一成同一种"事件流" |
| **Admission（准入）** | 监工对任务的放行检查：能力够不够、权限有没有、预算超没超、文件冲不冲突 |
| **Escalation（升级）** | 出了没办法自动解决的事（失败、冲突、超预算），停下来问用户 |
| **Usage（用量）** | 一次任务消耗了多少 token、多少钱、调了几次工具、跑了多久 |
| **Evidence（证据）** | 任务"做完了"的凭据。不能只听 Agent 自己说做完了，要有可核对的产物 |

### 1.3 官方资料核实情况（按 Agent 分组）

#### Pi —— ✅ 关键结论：Pi 是编程 Agent Harness，**不是**数据分析 Agent

用户的要求是对的，且我用三份独立证据确认：

1. **包名与自述**：`@earendil-works/pi-coding-agent`，`description` 字段原文是 `"Coding agent CLI with read, bash, edit, write tools and session management"`。
2. **官方文档第一句**（`docs\index.md`）：`Pi is a minimal terminal coding harness.`（"Pi 是一个极简的终端编程 harness。"）
3. **内置工具清单**（`docs\quickstart.md` + `docs\usage.md`）：默认四个工具 `read / write / edit / bash`；可选内置工具 `grep / find / ls`（Windows 上还有 `powershell`）。

**Pi 内置的工具里没有任何一个与数据分析相关。** 所以：

- ❌ **"Pi 擅长数据分析"这个说法不成立**，必须从 Agent 的定位里删掉。
- ✅ **数据分析应当被当作"可安装的 Skill"**。Pi 明确实现了 [Agent Skills 标准](https://agentskills.io/specification)：技能放在 `~/.pi/agent/skills/`、`~/.agents/skills/`、`.pi/skills/`、项目 `.agents/skills/`，每个技能是一个含 `SKILL.md` 的目录。Pi 甚至支持把 Claude Code 和 Codex 的技能目录直接挂进来（`docs\skills.md` 里给了 `"skills": ["~/.claude/skills", "~/.codex/skills"]` 的例子）。
- ❌ **不能继续把"数据分析"写成 Pi 的固有能力**。我没有找到任何证据表明用户用的 Pi 是另一种自研的数据分析 Agent——本机装的就是 `earendil-works/pi`，包名、仓库地址、文档全部对得上。任务书里那个说法应当被理解为"用户希望用 Pi 来做数据分析"，而不是"Pi 自带数据分析能力"。

### 2.2 Sidecar 负责的执行约束（Hermes 不能绕过）

这是本阶段最重要的安全设计。**凡是"约束"，都必须由 Sidecar 执行，不能寄希望于 Hermes 自觉。**

> ⚠️ **诚实标注（P0-3 修复）**：以下约束是**逻辑约束**，不是操作系统级隔离。
> 
> - `toolPolicy` / `writeScope` 只是"Sidecar 传给 Agent 的命令行参数"
> - Agent 收到参数后**可能不配合**（模型行为无法 100% 保证）
> - Pi 官方明确：**没有内置沙箱**（`docs/security.md`）
> - 真正的隔离需要容器、Worktree（阶段5）或操作系统权限边界
> 
> 阶段3 的约束能做到的是：**让正常配合的 Agent 受到限制**。恶意或故障的 Agent 仍可能越界。

| 约束 | Sidecar 怎么执行 | 为什么不能交给 Hermes | 实际约束力 |
|---|---|---|---|
| **能力校验** | 任务里的 `proposedWorkerId` 必须在能力登记表里存在且可用；Hermes 报一个不存在的 Agent → 直接拒绝 | Hermes 可能"幻觉"出一个不存在的 Agent | ✅ 强约束（Sidecar 控制） |
| **权限校验** | 任务声明的 `toolPolicy` 与 `writeScope` 会转成命令行参数（如 Pi 的 `--tools`、Claude 的 `--allowedTools`、Claude 的 `--permission-mode`） | 让 Agent 自己管自己，等于没有约束 | ⚠️ **逻辑约束**（依赖 Agent 配合） |
| **进程启停与状态** | 沿用阶段2 的 `AgentPool`，阶段3 增加"任务"这一层 | 已实现，扩展即可 | ✅ 强约束（操作系统进程管理） |
| **成本统计** | Sidecar 从各 Agent 的用量报告里抽数、记账、累计 | Hermes 拿不到别的 Worker 的账 | ✅ 强约束（Sidecar 控制） |
| **任务依赖** | `depends_on` 由 Sidecar 解析并排序；**不依赖的就并行，依存的必须串行** | 同上 | ✅ 强约束（Sidecar 控制） |
| **文件冲突保护** | Sidecar 维护"文件占用表"，准入时检查 | 同上 | ⚠️ **逻辑约束**（管不住 Agent 越界写） |
| **审计记录** | 每一次准入、启动、拒绝、重试、改派、终止都写一条带时间戳的记录 | 同上 | ✅ 强约束（Sidecar 控制） |
| **同一文件只能有一个主要修改者** | 见 §5.7（准入规则）与 §7 S8b（文件冲突保护）：`exclusive` 与 `shared` 两种占用级别 | 同上 | ⚠️ **逻辑约束**（管不住 Agent 越界写） |

**一句话总结**：Hermes 说"我想怎么做"，Sidecar 说"你可以怎么做"。**Hermes 的提案被拒绝时，必须把拒绝理由显示给用户**，不能让计划悄悄变形。

### 2.3 决定权的拆分：提案 vs 准入

这是我对用户设计**提出的一处修改建议**，理由在 §11。

```
用户一句话
    ↓
Hermes 产出「计划」——只是一张申请表，不是命令
    ↓
Sidecar 准入检查（每一项都能否决）
    ├─ 能力：这个 Agent 装了没、能不能干这个
    ├─ 权限：这次任务要动的文件/工具，允不允许
    ├─ 预算：这条子任务的预估花费在不在总额度内
    ├─ 冲突：要写的文件是不是已经被别人占了
    └─ 依赖：依赖的任务是否都已经成功
    ↓
通过 → 派发执行        不通过 → 记录理由，回给 Hermes 重规划一次；再不行 → 升级给用户
```

**为什么不能只让 Hermes 决定**：因为只有 Sidecar 知道"现在有几个任务在跑""这台机器上谁装了""这个文件谁正在写""今天已经花了多少"。Hermes 是通过一次性命令行调用的，**它看不到运行中的状态**。让它拍板 = 让它蒙着眼睛拍板。

### 2.4 AgentPool 与任务队列（解决 P0-2）

**问题重述**：阶段2 规定"同一 Agent 只能有一个实例"（`AgentPool` 用 `Map<agentId, PoolEntry>` 实现）。但阶段3 需要：
- 两个只读任务都想用 Pi → 能不能并行？
- 任务失败要重试 → 能不能同一个 Agent 重跑？
- 要换 Agent → Pi 跑完立刻换 Claude Code，还是要等？

**v2 方案**：保持阶段2 的单实例约束，**在上面加一层任务队列**。

```
TaskQueue（新增，Sidecar 层）
  ├─ 每个 Agent 一个队列：Map<agentId, Task[]>
  ├─ 准入通过的任务 → 进对应 Agent 的队列
  ├─ Agent 实例空闲时 → 从队列头取任务
  └─ 队列为空 → Agent 实例可以释放（保持阶段2 的按需启动）

AgentPool（保持阶段2，不改）
  ├─ 同一 Agent 只有一个实例
  ├─ 实例的生命周期：startAgent → running → stopAgent → idle
  └─ 实例退出时，从队列取下一个任务，没有就保持 idle
```

**这样做的好处**：
1. **不破坏阶段2**：`AgentPool` 的单实例、终止、Job Object 全部保持不变
2. **支持重试**：同一 Agent 的任务按顺序排队，第一次失败后第二次自动排在队尾
3. **支持换人**：任务从 Pi 队列移到 Claude 队列，各自独立调度
4. **代码清晰**：队列逻辑在 `TaskQueue` 类，池逻辑在 `AgentPool` 类，职责分离

**限制（阶段3 可接受）**：
- 同一 Agent 的任务**串行执行**（不并行）
- 两个只读任务都要用 Pi → 第二个排队等第一个结束
- 真正的"同一 Agent 多实例并行"留给阶段5（配合 Worktree）

**验收**：§8.6 第 28-31 条。

### 2.5 Hermes 规划模式（安全等级：逻辑隔离，**不是** OS 沙箱）

> **安全等级声明（本文件唯一权威表述）**：Hermes 在阶段3 的安全等级是**"逻辑隔离"**，**不是**操作系统级安全沙箱。以下所有约束都是 Sidecar 的**设计约定**，不构成对 Hermes 进程的真实权限限制。

**问题重述**：Hermes 的 `-z` 模式**自动绕过审批**，且它有 261 个工具（含 `terminal`、`browser`、`computer_use`）。由于 Hermes 进程以当前 Windows 用户身份运行，理论上它仍可能：
- 读取当前用户有权访问的其他文件；
- 读取环境变量、用户配置、自己的记忆/规则/Skills；
- 通过内置工具或子进程间接访问文件；
- 诱导 Sidecar 执行危险内容。

**v4 方案的目标**（改写为可实现的口径，**不声称"无法写文件"**）：

> 在 **S0 实测通过**且当前运行环境**不暴露项目路径**时，Hermes 被**逻辑限制**为只承担"规划"角色。这不是 OS 级安全隔离。

| 约束项 | 怎么做 | 为什么 |
|---|---|---|
| **工具白名单** | `-t read`（⚠️ `read` 是否为真实工具集名待验证，见 U3） | 不让它拿 `write` |
| **独立空目录** | 在临时空目录（如 `%TEMP%\agenthub-hermes-XXXXX`）里跑，**不挂载项目、不提供项目路径** | 减少它"看见真实项目"的途径 |
| **输入只给摘要** | 只给：① 用户目标 ② 四个 Agent 能力表 ③ 已完成任务摘要 | 不给文件列表、代码内容、绝对路径 |
| **输出 schema 校验** | 要求输出纯 JSON，并做 **Sidecar 侧 schema 校验** | 解析失败→重试2次→仍失败则升级 |
| **Sidecar 永不直接执行 Hermes 输出** | Hermes 输出的自然语言/计划**只作为提案**，任何实际动作都要经过准入 | 阻断"模型诱导 Sidecar 执行危险内容" |
| **超时** | `--run-budget` 设为 120 秒 | 防止卡死 |

**8 条必须遵守的红线**（P0-1 必须修改项）：
1. Hermes 不读取真实项目；
2. Hermes 运行在临时空目录；
3. 不提供真实项目路径；
4. 不提供 `write`；
5. 禁止读取密钥和用户配置（Sidecar 不注入含密钥的环境变量）；
6. 计划输出必须经过 Sidecar schema 校验；
7. Sidecar 永远不直接执行 Hermes 的自然语言输出；
8. **S0 验证失败则 Hermes 不得作为 Supervisor 使用**，降级为"用户手填计划或 Sidecar 使用固定测试计划"。

**如果 U3 验证失败（`-t read` 无法被证明有效）的降级方案**（P0-1 关键新增）：
- 若无法证明 `read` 是真实工具集名 / 无法排除 `terminal`、`browser`、`delegation` / Hermes 配置覆盖了命令行限制 / `-z` 绕过了工具集限制：
  - **阶段3 取消 Hermes 自动规划**；
  - 改用"用户手填 TaskProposal"或"Sidecar 内置固定测试计划"；
  - 阶段3 仍可推进其他功能（适配器、队列、持久化、成本），只是不启用 Hermes 自动拆任务。

**U3 失败后的阶段3 通过判定（P1-1 修复，消除"闭环 vs 降级"矛盾）**：

阶段3 的通过条件**取决于 U3 结果**，验收报告必须**固定使用三档结果**，不能用模糊的"部分通过"（P1-6 修复）：

| 阶段3 验收结论 | 判定条件 |
|---|---|
| **完整通过** | U3 通过，且 Hermes + Pi 都完成真实闭环，§8.1 第 3 条通过 |
| **核心闭环通过，Hermes 自动规划延期** | U3 失败，但"Sidecar 固定计划 + Pi 真实执行闭环"通过；验收报告明确标记"Hermes 自动规划未交付（延期）"，**不得伪装成完整通过** |
| **不通过** | Pi 真实执行闭环也未通过，或有 P0 级问题未解决 |

**关键结论**：
- "Hermes + Pi 硬性闭环" 是**设计目标**，不是无条件硬性要求。
- Hermes 自动规划能力是否纳入"阶段3 通过"的判据，**完全取决于 U3**。
- 验收报告最终只允许落在上面三档之一，**禁止写"部分通过"这类模糊词**。

**U3 验证项**（S0 必须做，结果决定 Hermes 能否当 Supervisor）：
1. 查证 `read` 是否为 Hermes 当前版本真实的工具集名（读 `toolsets.py`）
2. `-t read` 是否排除 `terminal`、`browser`、`computer_use`、`delegation`
3. Hermes 的配置文件（如 `config.yaml`）会不会覆盖命令行工具限制
4. `-z` 的自动绕过审批会不会绕过工具集限制
5. 在隔离空目录跑诱导性任务（"创建 a.txt"）→ 检查 a.txt 是否出现

**验收**：§8.3 第 12-13 条（验证 Hermes 看不到项目文件、且 U3 验证通过或按降级方案处理）。

## 3. 成本优先策略设计

### 3.1 原则

本阶段采用的调度原则，写成一句可执行的话：

> **优先使用"最便宜且足够胜任"的 Agent。**

**不写成"永远优先 Pi"。** 理由见 §3.5。

### 3.2 必须分开统计的 7 个量

这 7 个量口径不同，混在一起会得出错误结论。**界面上也要分开显示**，不要合成一个"智能分数"糊弄用户。

| # | 量 | 含义 | 从哪来 | 单位 |
|---|---|---|---|---|
| 1 | **token 数量** | 输入 + 输出 + 缓存读写的 token 总数 | Hermes 的 `--usage-file`；Pi 的 `--mode json` 事件里的 `usage`；Claude Code 的 `--output-format json` | 个 |
| 2 | **实际费用** | 这次真的花了多少钱 | 同上（如果 Agent 报的是"估算"，必须标出来） | 货币 |
| 3 | **重试次数** | 这条子任务失败重跑了几次 | Sidecar 自己记账（最可靠） | 次 |
| 4 | **工具调用** | Agent 调了几次工具（读文件、跑命令…） | Hermes 的 `--usage-file` 里有 `api_calls`；其余待验证 U5/U6 | 次 |
| 5 | **执行时间** | 从进程启动到退出的墙钟时间 | Sidecar 自己记账 | 毫秒 |
| 6 | **人工介入** | 用户被迫处理了几次（升级、改派、点确认） | Sidecar 自己记账 | 次 |
| 7 | **一次成功率 / 返工率** | 第一次就通过验收的比例 / 需要返工的比例 | Sidecar 自己记账（**这是最有价值的一项**） | 百分比 |

### 3.3 调度依据

**最终使用的指标是"每个成功完成任务的总成本"。**

它的定义（写清楚，避免实施时各人理解不同）：

```
每个成功完成任务的总成本
  = (这条任务链上所有 Agent 的费用之和
     + 失败重试花掉的费用
     + 验证任务花掉的费用)
    ÷ (最终真正通过验收的任务条数)
```

**为什么用它而不是"单次调用最便宜"**：一个便宜模型如果 3 次里有 2 次要返工，它的"每个成功任务成本"反而更贵。这个指标把返工和验证都算进去了，才是真实的账。

**阶段3 的现实约束（必须写进界面）**：

- 费用数据是**各 Agent 自己报的**，口径可能不一致。凡是拿不到实测费用的，一律显示"**估算**"，不显示"实际"。
- **本地没有可靠的单价表**（CC Switch 的 `model-pricing.json` 里 `models` 是空数组）。所以第一版的费用数据**以 Agent 自报为准**，Sidecar 不做二次计算。
- 拿不到费用的任务**照常记账**，费用的那一栏显示"未提供"，**不填 0**——填 0 会让"总成本"这个指标失真。

### 3.4 "Pi 优先"必须同时满足的 5 个条件

用户提出：Pi 优先必须满足"任务边界清楚 / 有自动测试或客观验收 / 可以安全回滚 / 不接触密钥和重要系统配置 / 运行在沙箱或受控目录"。这 5 条我全部保留，并**逐条落成可检查的字段**：

| 用户的条件 | 落成哪个字段 | 判定方式（Sidecar 自动检查） |
|---|---|---|
| 任务边界清楚 | `TaskEnvelope.goal` + `writeScope` + `toolPolicy` | `writeScope` 必须明确列出路径或"只读"；写不出具体路径 → 不满足 |
| 有自动测试或客观验收 | `TaskEnvelope.acceptance` | `acceptance.type` 必须是 `"command"`（跑一条命令看退出码）或 `"fileExists"` 等可机测类型；是 `"manual"` → 不满足 |
| 可以安全回滚 | **阶段3 无此字段**（`rollback` 已从 TaskEnvelope 移除，见 §5.2） | 见下方说明 |
| 不接触密钥和重要系统配置 | `TaskEnvelope.forbidden` | 默认禁止清单：`.env`、`config/agents.json`、`~/.pi`、`~/.claude`、`~/.codex`、`~/.cc-switch`、系统环境变量写入；命中即拒绝 |
| 运行在沙箱或受控目录 | `TaskEnvelope.cwd` + `allowedPaths` | `cwd` 必须在用户事先声明过的"受控目录白名单"里 |

**"可以安全回滚"这一条的诚实结论**：

- ⚠️ 阶段3 **不实现** Git Worktree（那是阶段5），所以**没有真正的回滚能力**。
- 因此阶段3 的**可行做法**只有两种，二者必须选一，**不能含糊**：
  - **做法 A（推荐）**：阶段3 只给 Pi 派**只读任务**（`toolPolicy` 只给 `read/grep/find/ls`，或用 `--tools` 白名单锁死）。写操作一律交给 Claude Code 或 Codex。等阶段5 的 Worktree 做好，再放开 Pi 的写权限。
  - **做法 B**：先对项目做一次 `git init` + 首次提交（这不是 Worktree 功能，只是让"回滚"这个概念成立），并把"任务开始前自动提交一次"作为 Pi 写任务的前置动作。
- **我推荐做法 A**，理由：做法 B 会在用户的项目里建立 Git 历史并产生提交，是对用户资产的实质改动，而且只解决一半问题（Agent 中途写坏、回滚仍是全量回滚）。做法 A 不引入任何新风险，且**不会假装有回滚能力**。

### 3.5 阶段3 对"Pi 优先"的最终结论

| 任务类型 | 阶段3 是否允许"Pi 优先" |
|---|---|
| 只读任务（看文件、统计、找信息、生成报告草稿） | ✅ **允许**，且应当在满足 §3.4 前 4 条时**优先派给 Pi** |
| 写文件的任务 | ❌ **不允许**。派给 Claude Code 或 Codex |
| 需要"能跑起来验证"的任务 | ⚠️ 需 `acceptance` 可机测；否则不满足 Pi 优先条件 |
| 涉及密钥、系统配置、安装卸载 | ❌ 一律不派，直接升级给用户 |

**这条结论与用户的直觉有出入（用户希望"优先用 Pi 省钱"），我在 §10 里把它列为争议决定之一，附反例。**

## 4. SQLite 持久化设计（解决 P0-1）

### 4.1 为什么需要持久化

**v1 的问题**：所有任务状态都在内存里（Sidecar 的 `Map` 和 `Array`），Sidecar 重启或崩溃后：
- 正在跑的任务：状态丢失，不知道跑到哪了
- 已完成的任务：历史记录全丢，无法查看"昨天干了什么"
- 成本统计：累计花费归零，无法做"本月总花费"
- 审计追溯：出了问题找不到当时是谁批准的、为什么批准

**v2 方案**：用 SQLite 存储所有需要跨会话保留的数据。

### 4.2 数据库位置与生命周期

| 项 | 值 |
|---|---|
| **数据库文件（正式运行）** | `<项目根目录>/.agenthub/tasks.db` |
| **数据库文件（验收测试）** | 放在**临时测试目录之外**，避免污染 `test-fixture/input/` 的哈希结果（见 §8.3） |
| **创建时机** | Sidecar 首次启动时，若不存在则创建 |
| **Schema 版本** | 用 `PRAGMA user_version` 管理，当前版本 **1** |
| **连接方式** | Sidecar 独占，Node.js 用 `better-sqlite3` |
| **事务** | 每个任务状态变更一个事务，保证原子性 |
| **备份** | 阶段3 不做自动备份，用户可手动复制 `.agenthub/tasks.db` |

> **为什么区分两套路径（P1-4 修复）**：正式运行时数据库自然放在项目根目录下；但验收第 11 条的"只读哈希比对"要求数据库不能落在 `test-fixture/` 内，否则 Sidecar 写数据库本身就会让目录哈希"变脏"。所以两种用途各用各的路径，互不冲突。

### 4.3 表结构

#### 表1：`tasks` —— 任务主表

```sql
CREATE TABLE tasks (
  task_id TEXT PRIMARY KEY,           -- 任务编号，UUID（Sidecar 生成）
  plan_id TEXT,                       -- 所属计划编号（来自 TaskProposal 的 planId，可空：用户手填任务可能无计划）
  proposal_id TEXT,                   -- 原始提案编号（来自 TaskProposal 的 proposalId，可空）
  parent_goal TEXT NOT NULL,          -- 用户最初的那句话
  goal TEXT NOT NULL,                 -- 这条子任务的目标
  proposed_worker_id TEXT NOT NULL,   -- Hermes 建议派给谁（proposedWorkerId）
  assigned_worker_id TEXT NOT NULL,   -- 准入后实际派给谁（assignedWorkerId，可能≠建议，且不允许为 hermes）
  model_alias TEXT NOT NULL,          -- fast/balanced/powerful
  reason TEXT NOT NULL,               -- 为什么这么派
  depends_on TEXT NOT NULL,           -- JSON 数组，依赖的 task_id
  created_at INTEGER NOT NULL,        -- 创建时间戳（毫秒）
  created_by TEXT NOT NULL,           -- hermes/user-manual/sidecar-fixed
  status TEXT NOT NULL,               -- created/admitted/queued/running/succeeded/failed/cancelled/escalated
  admitted_at INTEGER,                -- 准入通过时间
  started_at INTEGER,                 -- 实际开始执行时间
  finished_at INTEGER,                -- 结束时间
  exit_code INTEGER,                  -- 进程退出码
  result_summary TEXT,                -- Agent 的一句话总结
  acceptance_result TEXT,             -- passed/failed/notRun
  verify_task_id TEXT,                -- 独立验证任务的编号

  -- TaskEnvelope 的配置字段（JSON 存储）
  envelope_json TEXT NOT NULL,        -- 完整的 TaskEnvelope（包含 cwd/writeScope/toolPolicy/acceptance 等）

  FOREIGN KEY (verify_task_id) REFERENCES tasks(task_id)
);

CREATE INDEX idx_tasks_status ON tasks(status);
CREATE INDEX idx_tasks_proposed_worker ON tasks(proposed_worker_id);
CREATE INDEX idx_tasks_assigned_worker ON tasks(assigned_worker_id);
CREATE INDEX idx_tasks_created ON tasks(created_at DESC);

-- 追溯用：同一计划内的 proposalId 唯一（可空字段用 partial 语义，SQLite 用普通唯一索引时 NULL 不参与冲突）
CREATE UNIQUE INDEX idx_tasks_plan_proposal ON tasks(plan_id, proposal_id);
```

> **为什么拆分 `proposed_worker_id` / `assigned_worker_id`（P0-2 修复）**：`TaskEnvelope` 已经区分"Hermes 建议派谁"和"Sidecar 最终批准谁"。数据库若只用一个 `worker_id`，编码时会把二者混为一谈。一条逻辑任务需要**同时保留** Hermes 的最初建议（`proposed_worker_id`）和 Sidecar 的最终决定（`assigned_worker_id`），供审计追溯"为什么没按建议执行"。

#### 表2：`task_attempts` —— 重试记录

```sql
CREATE TABLE task_attempts (
  attempt_id TEXT PRIMARY KEY,        -- UUID
  task_id TEXT NOT NULL,              -- 归属任务
  attempt_index INTEGER NOT NULL,     -- 第几次尝试（0 开始）
  worker_id TEXT NOT NULL,            -- 这一次尝试实际使用的 Agent（assignedWorkerId 的具体值）
  run_id INTEGER,                     -- 对应 AgentPool 的 runId（启动失败时为 NULL，见下方说明）
  
  -- 进程身份（P0-1 新增，用于重启恢复 / 紧急停止 / 改派核对）
  pid INTEGER,                        -- 主进程 PID；启动失败时为 NULL
  parent_pid INTEGER,                 -- 父进程 PID（Sidecar 派生的直接父进程）
  process_group_id TEXT,              -- Windows Job Object 的进程组标识（若有）
  job_object_id TEXT,                 -- Windows Job Object 标识（若已创建并可查询）
  started_command TEXT,               -- 实际执行的命令行（用于审计与人工核对）
  
  started_at INTEGER NOT NULL,
  finished_at INTEGER,
  exit_code INTEGER,
  status TEXT NOT NULL,               -- running/succeeded/failed/cancelled
  failure_reason TEXT,                -- 失败原因
  switched_from TEXT,                 -- 如果是换 Agent，从谁换来的
  
  FOREIGN KEY (task_id) REFERENCES tasks(task_id),
  UNIQUE(task_id, attempt_index)
);

CREATE INDEX idx_attempts_task ON task_attempts(task_id);
CREATE INDEX idx_attempts_run ON task_attempts(worker_id, run_id);
CREATE INDEX idx_attempts_pid ON task_attempts(pid);
```

> **进程身份字段的写入与使用约定（P0-1 修复，详细规则）**：
> - **写入时机**：Agent 进程成功启动、拿到 OS 层 PID 后，立即在同一事务里写入 `pid` / `parent_pid` / `started_command`；`process_group_id` / `job_object_id` 在 Job Object 创建成功时写入。
> - **启动失败时**：这些字段全部为 NULL（进程根本没起来，自然没有 PID）。
> - **终止核对**：紧急停止 / 改派时，用 `pid` + Job Object 查询该任务进程树是否还存活，而不是靠"进程名"猜。
> - **Sidecar 重启后**：查 `pid` 是否仍存活——若存活则标记 failed（cannot reattach）；若已死则标记 failed（process not found）。**必须避免 PID 复用误杀**：核对时还要比对 `started_command` 与进程启动时刻（若可得），确认当前占用该 PID 的进程就是当时的 Agent 进程，否则视为"PID 已被系统重新分配"，不强行终止。
> - **为何 `run_id` 不够**：`runId` 是应用层运行编号，不是 Windows 进程身份。进程身份必须用 OS 的 PID + Job Object 标识落库，否则"按 PID 核对进程树"无法实现。

> **`run_id` 类型与可空性（P0-1 修复，采用方案 A）**：已核对 `shared/protocol.ts`，`runId` 的完整类型为 `number | null` 或 `number`（第 82、123、128、136、223、230、241、250、296、301 行）。因此 SQLite 中 `run_id` 定义为 **`INTEGER` 且允许为空**，与协议可空性一致。`attempt_id` 才是字符串 UUID，二者不要混淆。
>
> **启动失败时的 attempt 记录规则（P0-1 修复，关键规定）**：
> - 命令不存在 / 进程没起来等**启动失败**，**仍然创建一条 `task_attempts` 记录**（因为"启动失败"本身也是一次尝试，审计上需要留痕）。
> - 这条失败 attempt 的字段取值：`run_id = NULL`、`pid = NULL`、`parent_pid = NULL`、`status = failed`、`failure_reason` 写明原因（如 `command not found`）。
> - 只有 Agent **真正启动并获得 `runId`** 后，`run_id` 才非空。这样就区分了"没起来"（run_id 空）和"起来了"（run_id 有值）。

#### 表3：`task_events` —— 事件流

```sql
CREATE TABLE task_events (
  event_id TEXT PRIMARY KEY,          -- UUID
  task_id TEXT NOT NULL,
  attempt_id TEXT NOT NULL,
  sequence INTEGER NOT NULL,          -- 事件序号（同一 attempt 内单调递增，用于稳定排序）
  event_type TEXT NOT NULL,           -- taskStarted/taskOutput/taskToolCall/taskUsage/taskSucceeded/taskFailed/taskCancelled/taskEvidence
  timestamp INTEGER NOT NULL,         -- 毫秒时间戳
  payload TEXT NOT NULL,              -- JSON 格式的事件内容
  
  FOREIGN KEY (task_id) REFERENCES tasks(task_id),
  FOREIGN KEY (attempt_id) REFERENCES task_attempts(attempt_id),
  UNIQUE(attempt_id, sequence)
);

CREATE INDEX idx_events_task ON task_events(task_id, sequence);
CREATE INDEX idx_events_attempt ON task_events(attempt_id, sequence);
CREATE INDEX idx_events_type ON task_events(event_type);
```

> **为什么加 `sequence`**（P1-3 修复）：时间戳可能相同，或事件到达顺序与时间顺序不一致。`sequence` 由 Sidecar 在写入时对同一 `attempt_id` 单调分配，保证前端能稳定按顺序还原事件流。排序键改为 `(attempt_id, sequence)`。

> **`sequence` 的并发分配规则（P1-4 修复，必须明确）**：
> - **不允许多个异步回调直接写数据库**。每个 `attempt_id` 拥有**独立的串行事件队列**，事件先入队，再由**单一的写入器线程**按队列顺序落库。
> - `sequence` 的分配方式（二选一，实施时定死一种）：
>   - **方案 A（推荐）**：由每个 attempt 的**串行事件队列**在内存中逐条递增分配（每个 attempt 一个计数器），随之落库；同一 attempt 的写入天然串行，不会并发冲突。`UNIQUE(attempt_id, sequence)` 兜底。
>   - **方案 B**：在数据库事务内"读该 attempt 当前最大 `sequence` + 1，然后写入"，借助事务串行化避免重复。
> - **批量写入**时，按队列顺序一次性写若干条，序列连续递增。
> - **Sidecar 重启后继续分配**：重启恢复时先从库中读出该 attempt 已有事件的最大 `sequence`，下一个事件从"最大值 + 1"继续；但阶段3 重启后 running attempt 一律判 failed（§4.6），所以实际上"恢复后继续写同一 attempt 的事件"不会发生。这个规则仍然写出，是为了防止未来阶段4/5 做 detach+reattach 时出错。
> - **终态事件必须大于所有已写事件**：终态事件（taskSucceeded/taskFailed/taskCancelled）在所有普通事件写完、且 `sequence` 达到当前最大值之后，作为该 attempt 的序号最大的事件写入。

### 4.4 连接配置与写入时机

**连接配置（P1-4 修复）**：
- 打开数据库后**必须执行** `PRAGMA foreign_keys = ON;`，否则外键约束实际上不生效
- 用 `PRAGMA user_version` 管理 schema 版本（当前版本 **1**）

**写入时机表**：

| 数据 | 写入时机 | 事务边界 |
|---|---|---|
| `tasks` 表插入 | Hermes 产出 TaskProposal、Sidecar 补齐 TaskEnvelope、准入通过后 | 一批任务一个事务 |
| `tasks.status` 更新（非终态） | 状态变更时（queued→running） | 每次更新一个事务 |
| `task_attempts` 插入 | Agent 实例启动时 | 与 `tasks.started_at` 同一事务 |
| `task_events` 插入 | 收到适配器事件时 | **批量写入**（每 100 条或每 5 秒），但**终态事件见下** |
| `usage_records` 插入 | 任务结束、读到用量报告时 | **纳入终态事务（见下）** |
| `audit_log` 插入 | 准入拒绝、重试、换人、升级、手动操作 | 立即写入 |

**终态事务（P1-5 修复，一次原子提交）**：

任务结束（成功/失败/取消/升级）时，以下 5 个动作必须**在同一个事务里**一次性提交，不能拆成多个事务：

```
1. 写最后一个 task_events（taskSucceeded/taskFailed/taskCancelled）
2. 更新 task_attempts 为终态（succeeded/failed/cancelled）
3. 更新 tasks 为终态（succeeded/failed/cancelled/escalated）+ finished_at + exit_code
4. 写 usage_records（每个完成的 attempt 都写一条；没读到用量也要写，见下）
5. 写 audit_log（若本次结束涉及重试/换人/升级）
```

**每个完成的 attempt 都必须写一条 `usage_records`（P1-3 修复）**：

即使 Agent 没有返回用量，也要插入一条记录，字段取值：

```
cost_source  = unavailable
cost_amount  = NULL
tokens_input / tokens_output / tokens_cache_read / tokens_cache_write = 0
tool_calls = 0
api_calls = 0
wall_clock_ms = Sidecar 自行计算（finished_at - started_at）
```

**为什么必须这样**：如果 Agent 没报告用量就不写记录，会导致——时间线查不到这次 attempt 的耗时、费用统计和 attempt 数量对不上、`costSource=unavailable` 没有数据库落地、前端无法区分"没运行"和"运行了但没报告用量"。写一条 `unavailable` 记录后，这三者就被明确区分开了。

**为什么必须一个事务**（P1-5 修复）：如果拆成多个事务，中途崩溃会出现 `tasks` 显示 succeeded、`task_attempts` 仍是 running、`usage_records` 不存在、前端看不到 `taskSucceeded` 事件的状态撕裂。一个事务保证要么全成、要么全不生效。

### 4.5 读取时机

| 场景 | 读哪些表 |
|---|---|
| Sidecar 启动恢复 | `tasks` (status=running) + `task_attempts` (status=running) → 重建运行时状态 |
| 前端刷新页面 | `tasks` (最近 50 条) + `task_events` (每个任务最近 200 条) |
| 时间线展示 | `tasks` JOIN `task_attempts` JOIN `usage_records` |
| 成本统计 | `SELECT SUM(cost_amount) FROM usage_records WHERE cost_source='measured' AND recorded_at > ?` |
| 审计查询 | `audit_log` WHERE task_id=? 或 timestamp BETWEEN ? AND ? |

### 4.6 Sidecar 重启恢复逻辑

```
Sidecar 启动时：
  1. 打开数据库，检查 schema 版本
  2. 查询 tasks WHERE status IN ('running', 'queued')
  3. 对每个 running 任务：
     a. 查 task_attempts 拿到 worker_id、pid、run_id、started_command、job_object_id
     b. 用 pid + started_command 检查对应进程是否还活着（防 PID 复用，见下）
  4. 对每个 queued 任务：
     a. 重新加入对应 Agent 的队列
  5. 恢复准入检查的"文件占用表"（从 running 任务的 writeScope 重建）
     → 所有 running 都会被清理掉（见下），占用表实际为空
```

**Sidecar 重启后，旧进程仍存活时的实际清理策略（P0-2 修复，核心新增）**：

此前只说"标记 failed"，但那样会出现"数据库显示失败，Agent 仍在后台运行"的僵尸进程。正确做法是**既要标数据库失败，也要处理进程本身**：

```
步骤：Sidecar 启动发现旧 attempt 的 PID 仍存活：
  1. 先尝试按保存的 job_object_id 重新打开 Job Object 并整体终止
     → 但 Windows Job Object 通常不能用一个稳定字符串稳定地重新打开，
       阶段3 不把"重启后重开 Job Object"当作可靠手段
  2. 若无法重开 Job Object，改按 pid + started_command + 启动时刻核对身份
  3. 核对成功 → 终止主进程 + 已发现的子进程（尽力而为）
  4. 核对失败（PID 复用 / 无法确认身份）→ **不自动杀进程**，
     标记为"孤儿进程"，前端醒目标出 PID 与 taskId，提示用户手动处理
  5. 无论如何，数据库里该 attempt 标记 failed（sidecar restart）
```

**关于进程树身份的真实限制（P0-2 修复，诚实说明）**：
- Job Object、父 PID、进程组 ID 都不是"稳定可重开"的句柄。`job_object_id TEXT` 只是一条审计线索，**不能假设重启后能凭它重新获得整个进程树的管理权**。
- 子进程可能在运行期间继续创建；父 PID 可能退出或被复用。所以"完整进程树身份"无法被数据库**可靠**保存。
- 因此验收时：**若无法确认完整进程树已停干净，必须如实标记"无法确认"，不能声称"已停干净"**。
- 阶段3 的可靠兜底是：**Sidecar 存活期间**用 Job Object 实现整体终止（阶段2 已有）；**Sidecar 崩溃重启后**，退化为"尽力按 PID 清理 + 无法确认则报孤儿进程"。

**诚实说明**（其余）：
- ⚠️ "进程还活着但重开 Job Object 失败"是**阶段3 的妥协方案**；进程的 stdout/stderr 已被旧 Sidecar 占着，新进程接不上，无法继续接收事件
- ⚠️ 因此阶段3 的恢复策略是：**Sidecar 重启时，所有 running 任务一律标记为 failed + 尽力清理旧进程，queued 任务重新排队**
- ⚠️ 真正的"无损恢复"需要 Agent 实例支持"detach + reattach"，那是阶段4/5 的事

**验收**：§8.7 第 33-36 条 + §8.5 第 27 条（孤儿进程如实报告）。

## 5. Agent 角色定位与接口设计

> **角色三分（P1-1 修复，防止误派任务给 Hermes）**：
> - **Supervisor**：Hermes —— 只出 TaskProposal，不执行，不进入真实项目。
> - **Workers**：Pi、Claude Code、Codex —— 真正执行 TaskEnvelope。
> - **Fallback**：Sidecar 固定计划 / 用户手填计划 —— Hermes 不可用时的替代。
>
> **硬性规则**：`assignedWorkerId` **不允许为 `hermes`**。Hermes 只能以 `plannerId` / `supervisorId` 身份出现在计划元数据里，绝不能作为任务的实际执行者被派发。

| Agent | 角色 | 定位 | 适合的活 | 不适合的活 |
|---|---|---|---|---|
| **Hermes** | **Supervisor** | 中心调度、长期记忆、任务拆分、最终汇总 | 听懂目标、出 TaskProposal、攒经验、定时触发、汇总结果 | **不适合当执行手**：`-z` 自动绕过审批、261 个工具很难约束，U3 待验证。**仅作 plannerId，不作 assignedWorkerId** |
| **Pi** | Worker | 低成本首选执行者 | 只读检索、小范围明确改动、批处理脚本、固化 Skill | 代码库级重构、架构决策、需要权限隔离的场景 |
| **Claude Code** | Worker | 复杂代码库、重构、架构设计、高风险审查 | 跨文件重构、读懂陌生代码库、review | 廉价重复小事；PATH 入口当前是坏的（P6） |
| **Codex** | Worker | 本地工程执行、构建测试、调试、独立验证 | 跑构建、跑测试、调试 Windows、独立复核 | CLI 认证与路由待验证（U8） |

**关于"独立验证"的说明**：验证任务**必须派给与实现者不同的 Worker**。如果 Pi 写的，就别让 Pi 自己验。这不是洁癖——同一个 Agent 用同一套理解去验，会**系统性地漏掉同一类错误**。阶段3 把它写成强制规则（§5.7）。

### 5.0 必须设计的接口（9 项）

> **协议落地原则**（沿用阶段2 的铁律）：类型的**唯一出处**是 `shared/protocol.ts`。Rust 侧要手写对应的 `serde` 结构，**Rust 与 TS 之间没有编译期联动**——改字段必须三处同改（`shared/protocol.ts`、Rust 结构体、Sidecar 内部类型）。这仍然是本阶段最容易悄悄出错的地方。

### 5.1 `AgentCapability` —— 能力登记结构

| 字段 | 人话解释 | 谁填 |

| `id` | Agent 标识（`hermes` / `pi` / `claude` / `codex`） | 配置 |
| `label` | 界面上显示的名字 | 配置 |

### 5.2 `TaskProposal` 与 `TaskEnvelope` —— 两层任务结构（修复 P1-2）

**作用**：解决"Hermes 看不到项目文件，却要它生成完整执行字段"的矛盾。任务从中拆成两层：**Hermes 只出高层提案，Sidecar 补齐执行细节**。

> **为什么分两层**（P1-2 修复）：Hermes 的输入只有"用户目标 + 能力表 + 摘要"，**看不到真实目录结构和文件**。如果让它生成 `cwd`、`writeScope`、`allowedPaths` 这类需要知道 Windows 绝对路径的字段，它只能**瞎猜**，Sidecar 会大量拒绝，或被迫接受错误路径。所以：**提案归 Hermes，信封归 Sidecar。**

#### 第一层 `TaskProposal`（Hermes 的输出，或用户手填）

> **关于 `planId` 与 `proposalId`（P1-2 修复，含生成时序）**：一次 Hermes 规划会产生一个**计划**，计划里包含若干条**提案**。这两个编号的**生成时序固定如下**，避免"谁生成 Plan的 planId"的歧义：
> ```
> 1. Hermes 输出整批提案，每条带 proposalId（Hermes 生成，计划内唯一）
> 2. Sidecar 收到整批提案后，统一生成一个 planId（Sidecar 负责）
> 3. Sidecar 把同一个 planId 写回整批任务
> ```
> 即：**`proposalId` 由 Hermes 生成，`planId` 由 Sidecar 在收到整批后生成/补齐**，Hermes 不负责、也不需要提前生成 planId。`proposalId` 只在**同一 `planId` 内**唯一。这两层编号都要落库，才能追溯"这条任务来自哪一次计划、Hermes 原始建议是什么、Sidecar 如何转换"。

| 字段 | 人话解释 | 谁填 |
|---|---|---|
| `planId` | 本次计划的唯一编号（Sidecar 生成，同一批 proposal 共享） | Sidecar |
| `proposalId` | 本次计划内的临时编号（**必须在同一次计划内唯一**） | Hermes |
| `goal` | 这条子任务要达成什么（一句话） | Hermes |
| `proposedWorkerId` | 建议派给谁 | Hermes |
| `modelAlias` | 建议用哪个档次（`fast` / `balanced` / `powerful`） | Hermes |
| `reason` | **为什么这么派**（人话） | Hermes |
| `dependsOn` | 依赖哪些任务（**只能引用同一计划内的 `proposalId`**） | Hermes |
| `acceptanceSuggestion` | 建议"怎么算做完"（人话描述，如"生成一个 report.md"） | Hermes |
| `verificationRequired` | 是否建议独立验证（布尔） | Hermes |
| `proposedVerifierWorkerId` | 建议由谁验证（可空） | Hermes |

**注意**：`TaskProposal` **不包含**任何 Windows 路径、不包含 `cwd`/`writeScope`/`allowedPaths`/`forbidden`/`toolPolicy`/`budget`。这些是执行细节，Hermes 不给、也给不准。

#### 第二层 `TaskEnvelope`（Sidecar 补齐后产出，真正用来执行）

| 字段 | 人话解释 | 谁填 |
|---|---|---|
| `taskId` | 任务编号（Sidecar 生成 UUID） | Sidecar |
| `protocolVersion` / `schemaVersion` | 协议与结构版本 | Sidecar |
| `planId` | 所属计划编号（转存自 TaskProposal） | Sidecar |
| `proposalId` | 原始提案编号（转存自 TaskProposal，用于追溯） | Sidecar |
| `parentGoal` | 用户最初那句话 | Sidecar |
| `goal` | 来自 TaskProposal | Sidecar（转抄） |
| `proposedWorkerId` | Hermes 建议派谁 | Sidecar（转抄） |
| `assignedWorkerId` | **准入后实际分派谁**（可能与建议不同，**不允许为 hermes**） | Sidecar |
| `modelAlias` | 用哪个档次 | Sidecar（可下调） |
| `reason` | 为什么这么派 | Sidecar（转抄+补充） |
| `dependsOn` | 依赖的任务编号（转成真实 taskId） | Sidecar |
| `cwd` | 在哪个目录干活 | **Sidecar** |
| `writeScope` | 允许写哪些路径（glob），空=只读 | **Sidecar** |
| `allowedPaths` | 允许读哪些路径 | **Sidecar** |
| `forbidden` | 禁止碰的东西（默认清单） | **Sidecar** |
| `toolPolicy` | 允许/禁止哪些工具 | **Sidecar** |
| `acceptance` | 怎么算做完（机测类型，见 §5.6） | **Sidecar**（从 acceptanceSuggestion 转成机测） |
| `failureRecovery` | 写任务失败后的恢复模式（见下方说明） | **Sidecar**（默认 `no-retry-after-write`） |
| `verificationRequired` | 是否独立验证 | Sidecar（转抄，可强制） |
| `verifierWorkerId` | 谁验证（**必须≠实现者**） | Sidecar |
| `budget` | 花费上限 | **Sidecar** |
| `createdBy` | `hermes` / `user-manual` / `sidecar-fixed` | Sidecar |

> **`failureRecovery` 字段（P1-3 修复，机器可读）**：写任务失败是否允许重试，必须由**机器可读字段**表达，不能靠 Sidecar 猜自然语言。取值：
> ```
> failureRecovery:
>   mode: "no-retry-after-write"      ← 阶段3 默认，写任务失败且改了文件→不重试、直接升级
>        | "allow-incremental-retry"  ← 仅当用户手动确认"可接受增量修改"才允许
> ```
> 阶段3 默认固定为 `no-retry-after-write`；`allow-incremental-retry` 只由用户手动确认后设置，调度器不得自行切换。

#### 两层之间的转换规则

1. Hermes 出 `TaskProposal` 数组 → Sidecar schema 校验（P0-1 红线第 6 条）
2. 校验通过 → Sidecar 补齐 `TaskEnvelope`（填 cwd、writeScope、toolPolicy、budget 等）
3. 补齐后的 `TaskEnvelope` 才进入准入检查（§5.7）
4. 被拒时，把拒绝理由回给 Hermes 重规划（有界，见 §2.5）

#### `proposalId → taskId` 依赖映射算法（P1-2 修复，必须明确定义）

Hermes 用 `proposalId` 表达依赖，Sidecar 必须把它转成真实的 `taskId`。规则如下：

| 规则 | 明确要求 |
|---|---|
| `proposalId` 唯一性 | 同一次计划内 `proposalId` **必须唯一**；发现重复 → 整批拒绝，回给 Hermes 重规划 |
| `dependsOn` 引用范围 | 只能引用**同一次计划内**的 `proposalId`；引用不存在的编号 → 整批拒绝 |
| 跨计划引用 | 禁止引用旧计划的编号。每个计划是一个独立命名空间，`proposalId` 不跨计划复用 |
| `taskId` 生成时机 | Sidecar 接受整批计划、schema 校验通过后，**统一为每条生成 UUID `taskId`** |
| 映射过程 | Sidecar 先建立一张 `Map<proposalId, taskId>`，再据此把每条任务的 `dependsOn` 从 `proposalId` 列表转成 `taskId` 列表 |
| 映射失败 | 整批拒绝（不是只拒绝某一条），理由写清是哪条 proposalId 解析失败，回给 Hermes 重规划 |
| 结果 | `TaskEnvelope.dependsOn` 存的是**真实 taskId**，不再含 proposalId |

**示例**：Hermes 输出 `[A, B, C]`，其中 `C.dependsOn = ["A","B"]` → Sidecar 生成 `{A: t1, B: t2, C: t3}` → `C.dependsOn` 最终为 `[t1, t2]`。

**原任务书调度 JSON 的关系**：任务书的 `id / agent / model / reason / task / depends_on` 被拆分到两层里，**信息全部保留**，`id` 拆成 `proposalId`（Hermes 临时编号）+ `taskId`（Sidecar 正式编号），`agent` 拆成 `proposedWorkerId`+`assignedWorkerId`。差异说明见 §10。

**验收**：Sidecar 接收一个 **TaskProposal**（不含任何路径、只有 proposalId 表达依赖），能：① 校验 proposalId 唯一、dependsOn 不越界；② 补齐成带完整 `cwd`/`writeScope`/`toolPolicy` 的 **TaskEnvelope**；③ 把 `dependsOn` 里的 proposalId 转成真实 taskId。检查方法：让任务声明"只读"，任务结束后对目标目录做哈希，确认无新文件、无改动。

### 5.3 `AgentAdapter` —— 统一适配器接口

**作用**：四个 Agent 的命令行参数、输出格式、用量汇报方式都不一样。适配器把它们**统一成同一种事件流**给 Sidecar。

统一事件流（所有 Agent 都归一化成这几种）：

| 事件 | 含义 | 谁来产生 |
|---|---|---|
| `taskStarted` | 进程起来了 | Sidecar |
| `taskOutput` | 有输出（原样转发给界面） | 适配器 |
| `taskToolCall` | Agent 调了一次工具 | 适配器（能解析就发，不能就跳过） |
| `taskUsage` | 用量的一个增量或快照 | 适配器 |
| `taskSucceeded` | 进程退出，退出码 0 | Sidecar |
| `taskFailed` | 进程退出，退出码非 0 / 启动失败 | Sidecar |
| `taskCancelled` | 被用户或 Sidecar 主动终止 | Sidecar |
| `taskEvidence` | 找到了一份可核对的产物 | 适配器 + Sidecar |

每个适配器要实现的方法：

| 方法 | 干什么 | Pi 的实现要点 | Hermes 的实现要点 |
|---|---|---|---|
| `probe()` | 探测装没装、版本多少 | 跑 `pi --version` | 跑 `hermes --version` |
| `buildArgs(envelope)` | 把任务表格翻译成命令行参数 | `-p "<提示词>"`、`--model <真实模型>`、`--tools <白名单>`、`--no-session` | `-z "<提示词>"`、`--model`、`--provider`、`-t <工具集>`、`--usage-file <临时路径>`、`--max-turns`、`--run-budget` |
| `buildEnv(envelope)` | 组装环境变量 | 沿用阶段2 的三层注入，**但要去掉无效的 `ANTHROPIC_MODEL`**（P2） | 走 Hermes 自己的 provider 配置（**不经 CC Switch**，P 见 §1.3） |
| `parseOutput(line)` | 把一行输出翻译成统一事件 | 默认模式按纯文本转发；`--mode json` 时解析事件对象 | `-z` 模式只有纯文本；用量从 `--usage-file` 读 |
| `readUsage(tempPath)` | 运行结束后读用量报告 | 从 json 事件里累加 `usage.cost` | 读 `--usage-file` 写的 JSON |
| `cancel()` | 终止（沿用阶段2 的终止机制） | 同 | 同 |

**验收**：用**同一份** TaskEnvelope 分别跑 Pi 和 Hermes，Sidecar 产生的统一事件流**结构完全相同**；界面上看到的两条任务卡片的字段一样多。跑一个不存在的命令 → 得到 `taskFailed` 而不是崩溃。

### 5.4 调度决策结构（**必须包含选择理由**）

**作用**：把"为什么派给这个 Agent"这件事**存下来**。用户事后必须能看懂"为什么这次用了贵的"。

| 字段 | 人话解释 |
|---|---|
| `decisionId` | 决策编号 |
| `taskId` | 对应哪条任务 |
| `chosenWorkerId` | 最终选了谁 |
| **`reason`** | **为什么选它**（必填，人话，不能是空话） |
| `alternatives` | 还考虑过谁、为什么没选 |
| `admissionResult` | 准入结论：`accepted` / `rejected` / `downgraded`（降级） |
| `rejectionReasons` | 被拒的话，逐条写清是哪一项没过（能力/权限/预算/冲突/依赖） |
| `ruleMatched` | 命中了哪条规则（如"只读任务 → 优先 Pi"） |
| `costEstimate` | 预估花费，并标明是估算还是实测 |
| `decidedBy` | 谁做的决定：`hermes` / `sidecar-rule` / `user-manual` |
| `decidedAt` | 什么时间决定的 |

**验收**：时间线上每一条任务，点开后**必须能看到一句人类能读懂的"为什么派给它"**；被拒的任务必须能看到**具体是哪一项没过**。构造一个必被拒的任务（比如让 Pi 去写 `.env`），确认拒绝理由准确指出"碰到了禁用清单"。

### 5.5 成本与使用量记录结构

| 字段 | 人话解释 |
|---|---|
| `taskId` / `workerId` / `runId` | 归属 |
| `tokensInput` / `tokensOutput` / `tokensCacheRead` / `tokensCacheWrite` | 各类 token 数 |
| `costAmount` / `costCurrency` | 费用 |
| **`costSource`** | **这是关键**：`measured`（Agent 实测上报）/ `estimated`（Agent 估算）/ `unavailable`（拿不到） |
| `toolCalls` | 工具调用次数 |
| `wallClockMs` | 花了多久 |
| `retryIndex` | 这是第几次尝试（0 = 第一次） |
| `humanInterventions` | 这次任务里用户介入了几次 |
| `apiCalls` | 接口调用次数 |

**必须遵守的显示规则**：

1. **`costSource` 是 `unavailable` 时，费用栏显示"未提供"，绝不填 0。**
2. **`estimated` 必须显示成"约"**，不能和 `measured` 长得一样。
3. 汇总时，**"总成本"要单独标出其中有多少是估算的**。

**验收**：跑一次真实任务后，时间线上能看到 token 数、费用（带"约"字或"未提供"）、重试次数、耗时；**故意把用量文件删掉**再跑一次 → 界面显示"未提供"，**不崩溃、不显示 0**。

### 5.6 执行结果与证据结构

**作用**：**不能只听 Agent 自己说"我做完了"。** 每一条"成功"都必须挂着一份可核对的凭据。

| 字段 | 人话解释 |
|---|---|
| `taskId` | 归属 |
| `status` | `succeeded` / `failed` / `cancelled` / `escalated` |
| `exitCode` | 进程退出码 |
| `summary` | Agent 自己说的一句话总结（**只是说法，不是证据**） |
| **`evidence`** | **证据数组**（见下表） |
| `acceptanceResult` | 验收结论：`passed` / `failed` / `notRun` |
| `artifacts` | 产生的文件（路径 + 大小 + 修改时间 + **哈希**） |
| `verifyTaskId` | 独立验证任务的编号（如果做了） |

证据的类型（`evidence` 数组里每一项）：

| 类型 | 含义 | 怎么产生 |
|---|---|---|
| `commandExit` | 跑了一条命令，退出码是几 | Sidecar 跑 `acceptance.command` |
| `fileHash` | 某个文件在任务前后的哈希变了/没变 | Sidecar 自己算 |
| `fileExists` | 某个文件出现了/消失了 | Sidecar 自己查 |
| `diffSummary` | 改了哪些文件、增删多少行 | Sidecar 自己跑 `git diff --stat`（⚠️ 项目不是 git 仓库，需先解决 P4）或做目录快照比对 |
| `agentClaim` | **Agent 的自述**（明确标注"这是自述，不是证据"） | 适配器 |

**验收**：故意让一个 Agent"谎报成功"（比如跑一个退出码为 1 的脚本，但脚本打印"全部完成"）→ Sidecar **必须判为失败**，因为证据是"退出码 1"，不是它的自述。这条是本设计的关键，必须有针对性测试。

### 5.7 失败、重试、换 Agent 和升级规则

规则表（**Sidecar 执行，Hermes 无权修改**）：

| 情况 | 处理 | 上限 |
|---|---|---|
| 进程启动失败（命令不存在） | 立刻失败，**不重试**（重试也不会好），把原因直接给用户 | 0 次 |
| **只读任务** 退出码非 0 | 重试，**同一个 Agent**，并把上次的错误输出附给下一次 | 默认 **1 次** |
| **写任务** 退出码非 0，且检测到文件变化 | **不自动重试、不自动换 Agent**，直接升级给用户（见下方说明） | 0 次 |
| **写任务** 退出码非 0，且**未**检测到文件变化 | 可重试 1 次（同一 Agent） | 默认 **1 次** |
| 只读任务重试后仍失败 | **换 Agent**：换一个能力够的（Pi 失败 → Claude Code） | 换 **1 次** |
| 换 Agent 后仍失败 | **升级给用户**，附上每次尝试的失败原因与已花的钱 | —— |
| 验收未通过（acceptance failed） | 与对应类型（只读/写）同一条路径处理 | —— |
| 触碰禁用清单（密钥/系统配置） | **不重试、不换人**，直接拒绝并升级 | —— |
| 文件冲突（要写的文件被别人占着） | 排队等待；超时后升级 | 排队上限 **5 分钟** |
| 超预算（金额/时长/次数） | **立即终止**该任务并升级，附上已经花掉的量 | —— |
| 用户手动终止 | 立刻终止，标记 `cancelled`，**不算失败**，不影响成功率统计 | —— |
| Agent 卡住不退出 | 有墙钟上限，到点强杀，标记 `failed`（超时） | 每个 Agent 的 `budget.maxWallClockMs` |

**写任务失败禁止自动重试的理由**（P1-6 修复）：
- 阶段3**没有真正的回滚能力**（§3.4）。一个写任务可能在失败前已经**部分修改了文件**。
- 如果自动重试，第二次会**在已经污染的文件上继续**，结果不可预测；换 Agent 也会接着错误状态做。
- 因此：**写任务失败且检测到文件变化 → 默认不自动重试、不自动换 Agent，直接升级**，把"文件已被改动"作为关键信息告诉用户。
- 只有任务**明确声明"可接受增量修改"**时才允许重试；阶段3 不允许把"失败后回到原状态"称为回滚。

**"文件变化检测"的明确定义（P1-5 修复，消除临时猜测）**：

阶段3 采用"快照比对"方法来检测写任务是否改了文件，规则如下：

| 规则 | 明确要求 |
|---|---|
| 快照时机 | 任务开始前，先对受控范围做一次**内容快照** |
| 快照范围 | 写任务 → 解析后的 `writeScope`；只读任务 → `test-fixture/input/` |
| 记录什么 | 新增文件、删除文件、**内容哈希变化**（不依赖文件大小/修改时间，因为那不可靠） |
| 是否跟踪目录 | 是，递归遍历受控范围 |
| Windows 路径大小写 | 归一化（统一小写）后比较，避免 `A.txt` 和 `a.txt` 误判 |
| 符号链接 / junction | 阶段3 不跟踪链接目标内容，只记录链接本身；**若路径无法安全解析（如指向项目外），该任务直接拒绝** |
| 快照自身影响 | 快照**只读**，不写入任务目录；快照数据存在 Sidecar 内存或临时区，不污染受控目录 |
| 排除项 | 数据库（`.agenthub/tasks.db` 在项目外）、日志、临时目录、`output/` 目录 |
| 结束比对 | 任务结束后，重新扫描同一范围，与快照比对差异 |

**结论**：写任务结束（无论成功失败）都做一次快照比对。若比对出"内容哈希变化且任务退出码非 0"→ 判定"文件已改动"→ 不重试、不换人、直接升级。

**强制规则（不是建议）**：

- **验证任务必须换人**：实现者是谁，验证者就不能是谁。
- **验证任务单独记账**，计入"每个成功完成任务的总成本"。
- **重试和换 Agent 都要写审计记录**，界面上要看得到"这次换了人，因为上次失败在 X"。

**验收**：构造一个必然失败的**只读**任务（退出码 1 的脚本）→ 观察它重试 1 次、换 1 个 Agent、然后升级给用户，界面上**三次尝试都能看到**，费用把所有尝试都算进去了。再构造一个**写任务失败且改了文件**的场景 → 确认它**不自动重试**、直接升级。

### 5.8 手动改派与紧急停止

| 操作 | 入口 | 行为 | 失败路径 |
|---|---|---|---|
| **单条任务改派** | 时间线上任务卡片的"改派"按钮 | ① 先**真的终止**原任务（沿用阶段2 的终止机制，确认进程已退出）② 用同一个 `taskId` 起一条新任务，`assignedWorkerId` 换成用户选的 ③ 记一条审计（`decidedBy: user-manual`） | 原任务 3 秒内没退出 → **不改派**，提示"原任务仍在运行，请先终止"，绝不"覆盖"运行中的任务 |
| **整条任务链改派** | 对话级操作 | 还没开始的任务直接换人；**已经跑完的任务不重跑**（除非用户明确选"从这一步重跑") | 同上 |
| **单条任务终止** | 沿用阶段2 的逐个终止 | 不会扩散到别的任务 | —— |
| **紧急停止（全部）** | 顶部栏一个显眼的按钮，**两步确认** | ① Sidecar 停止接受新的准入 ② 终止所有运行中的任务 ③ **顺便终止 Hermes 自己**（如果它还在跑）④ 写审计 ⑤ 界面进入"已全部停止"状态 | 有进程未退出 → 报告具体 PID 和 taskId，不假装停干净了 |

**三层身份必带（P1-3 修复）**：所有终止、改派、事件操作，请求与记录都必须携带 `taskId + attemptId + runId`。原因：防止旧 attempt 的迟到终止事件误杀新 attempt。若某个终止请求的 `runId` 已经过期，Sidecar 必须拒绝并忽略。

**改派时的 taskId / attemptId / runId 状态关系（验收问题3 修复，写入正式状态机规则）**：

改派**复用同一个 `taskId`**，但必须遵守以下规则（这些是状态机规则，不是验收描述）：

| 规则 | 明确要求 |
|---|---|
| `taskId` 不变 | 改派不新建 `tasks` 记录，仍用原 `taskId` |
| `attemptId` 新建 | 新旧分离：旧 attempt 保留（标记 `cancelled` 或 `switched_from`），新改派产生**新的 `attemptId`** |
| `runId` 新建 | 新 attempt 用新的 `runId`（应用层运行编号，不复用） |
| 任务最终状态 | 由**最新有效 attempt** 决定；旧 attempt 的迟到事件只能写历史，**不能改变任务当前状态** |
| 旧 attempt 迟到事件 | 携带旧 `runId` 的迟到事件，Sidecar 校验 `runId` 过期后**丢弃**，不作用于新 attempt |
| 审计 | 记一条 `audit_log`（`event_type=switch`，`decidedBy=user-manual`），保留旧 attempt 与新 attempt 的对应关系 |

**"紧急停止"必须能杀掉 Hermes**：因为 Hermes 是链路里最可能"自己动手"的一环，停不掉它就等于没停。若 Hermes 拉起了子进程树，用 Windows Job Object 回收（已见于阶段2）。

**验收**（P1-8 修正判据）：
1. 三条任务并行跑（两读一写），点"紧急停止" → 按任务登记的 PID 核对，**这三条任务对应的进程树消失**；用户自己开的其他 Node/Python **不受影响**；界面显示"已全部停止"。
2. 任务 A 运行中改派给**另一个可用 Worker**（如 Claude Code 或 Codex）→ 任务 A 必须**先真的死掉**（用 `runId` 核对，不是裸进程号），新任务用的是新 Worker 与新 attemptId。
3. 故意造一个 3 秒内退不掉的进程 → 紧急停止后界面**如实报告具体的 PID + taskId**，不能显示"全部已停止"。

### 5.9 任务时间线需要展示的内容

按设计规范 §4.1 / §4.2 的样式来，**内容**如下：

**顶部总览条**：

| 显示什么 |

## 7. 实施步骤

每个步骤都能**独立验收**，做不完不许往下走。格式：目的 → 输入 → 输出 → 状态变化 → 失败路径 → 怎么验收。

### S0. 环境核对（**先做这个，不许跳**）

> **S0 拆成四步（P1-7 修复）**，把"只读探测"与"修改配置"彻底分开，修改动作永远不是默认项。

#### S0a. 只读环境探测

- **目的**：只读取、只探测，**不写任何东西**。
- **要做的事**：
  1. 探测 CC Switch 实际监听端口，对比 `config/agents.json` 里写的端口（P1-1 原 P1）
  2. 对 `config/agents.json` 里每个 Agent 的 `*_BASE_URL` 发 HTTP OPTIONS 探测连通性
  3. 实测 U2（`hermes -z` 跑不跑得通）、**U3（§2.5 的 Hermes 安全验证）**、U8（Codex CLI 认证与路由）
  4. 定位 Claude Code 的真实可用入口（当前入口是否损坏、真实二进制在哪）
- **输出**：原始探测结果（命令 + 输出），不产出判断。

> **网络探测的安全规则（P1-5 修复，避免非预期代理行为）**：
> 1. **默认不发送 API 密钥**：OPTIONS 探测不带认证头、不带密钥。
> 2. **只访问本机地址或配置中明确写出的地址**，不访问任何未在配置里出现的地址。
> 3. **OPTIONS 失败只能记为"OPTIONS 不支持"，不能直接判 Agent 不可用**——某些代理不支持 OPTIONS，但实际 POST 调用可能正常。
> 4. 必要时用无成本、最小请求做非破坏性验证；**不把探测请求计入任务费用**，或明确标为"环境探测"。

#### S0b. 输出核对报告 + 修改建议

- **目的**：把 S0a 的原始结果整理成可读的核对报告。
- **要做的事**：对每项给出结论（可用/不可用/待验证）+ **修改建议**（如"端口 8787 应改为 15721"、"Claude 入口应指向某路径"）。P4（git 回滚）标注为"待用户拍板"。
- **输出**：`阶段3-环境核对表.md`（新建，包含结论 + 建议 + 证据）。
- **验收**：核对表里每项都有"实测结果 + 证据 + 修改建议"，没有"应该可以"这类词。

#### S0c. 用户确认后修改配置（**必须用户确认，缺一不可**）

- **目的**：只有在用户明确确认后，才修改环境配置。
- **前置条件**：用户对 **S0b 产生的《阶段3-环境核对表.md》**逐条确认。
- **执行铁律**：① 先备份 `config/agents.json` ② 记录修改前后差异 ③ 只改 `config/agents.json`，**不动用户全局装的软件**。
- **用户不确认时**：阶段3 只能使用现有配置，不做任何改动。接不上的 Agent 记为"不可用"，按"接得上的那些"继续做。

#### S0d. 修改后复验 + 阶段2 回归

- **目的**：改完配置后，确认没改坏东西。
- **要做的事**：重新跑 S0a 的探测，确认修改生效；重跑 §8.9（第 41-55 条，15 条）+ §8.10（第 56-60 条，5 条）阶段2 回归，共 20 条，确认旧功能未坏。
- **验收**：修改生效 + 阶段2 回归通过；若修改失败，用备份恢复原文件并如实记录。

- **状态变化**：无（全程不涉及运行时任务状态）。
- **失败路径**：某项 Agent 确实接不上 → **明确记"接不上 + 原因"**，阶段3 按"接得上的那些"继续做，**不假装四个都接上了**。

### S1. 能力登记 + 可用性探针

- **目的**：让界面和调度器都能知道"现在到底有哪些 Agent 真能用"。
- **输入**：`config/agents.json`。**输出**：`AgentCapability`（§5.1）+ 界面上的 Agent 列表显示版本与不可用原因。
- **状态变化**：新增"能力登记"这一层，**不改动**阶段2 已有的池逻辑。
- **失败路径**：探测超时 → 该 Agent 标记为"探测失败，原因：超时"，**不阻塞其它 Agent**。
- **验收**：把某个 Agent 的 `command` 改成不存在的命令 → 变红 + 原因；其余三个照常。界面显示的版本号与在命令行里跑 `--version` 得到的一致。

### S2a. 适配器接口定义

- **输入**：`TaskEnvelope` 结构定义。**输出**：`sidecar/src/adapter.ts`（新建），定义 `AgentAdapter` 接口。
- **要做的事**：
  1. 定义 `AgentAdapter` 接口：`probe()` / `buildArgs()` / `buildEnv()` / `parseOutput()` / `readUsage()` / `cancel()`

- **失败路径**：N/A（纯类型工作）。
- **验收**：`adapter.ts` 编译通过，导出的类型能被 TS 正确识别。

### 8.3 安全（6 条，**这一组最重要**）

> **只读哈希比对范围定义（P1-7 修复）**：验收第 11 条的"全量哈希比对"必须在**统一的受控测试目录**里做，否则会误伤数据库/日志/临时文件。定义如下：
> ```
> test-fixture/
>   input/       ← 只读任务只能读、不能改；对 input/ 全量哈希比对
>   expected/    ← 预期产物（只读）
>   output/      ← 任务输出写入这里，不进 input/
> ```
> 规则：数据库 `.agenthub/tasks.db` 放在**项目目录之外**；日志、Hermes usage 文件、临时目录放在 `test-fixture/` 之外；**只对 `input/` 做哈希**；哈希只跟踪**文件内容**，不跟踪文件权限、修改时间、符号链接/junction。

> **"只读"的真实含义（P1-4 修复，必须让用户看懂）**：
> 所谓"只读"**不是操作系统的权限禁止**，而是三层合力——① 计划要求只读 ② Agent 工具参数限制（如 Pi 的 `--tools read,grep,find,ls`）③ 执行前后快照对比。如果 Agent 通过未受控的 PowerShell、扩展、配置加载等路径写入目录，Sidecar **只能事后发现、不能事前阻止**。
> 所以阶段3 的只读能力本质是"**发现异常后报警**"，不是"**从系统权限上禁止异常**"。验收第 11 条的结论也因此只能写成"未发现内容变化"，不能写成"Pi 被安全地限制为只读"。

| # | 验收项 | 判据 |
|---|---|---|
| 11 | **只读任务：当前配置下未发现内容变化**（P1-4 措辞修正） | 对 `test-fixture/input/` 做全量哈希比对，任务前后**内容一致**；结论表述为"在当前测试任务 + 当前工具配置下，未发现 input/ 内容变化"，**不表述为"Pi 被安全地限制为只读"** |
| 12 | **Hermes 看不到项目文件** | U3 验证通过（或按降级方案处理），Hermes 无法读取真实项目路径 |
| 13 | **Hermes 不写文件** | U3 验证：`-t read` 若能证明有效则验证其不产生文件；若无法证明有效，走降级方案（取消 Hermes 自动规划） |

## 11. 我认为最有争议的三个决定

> 用户要求我"不要为了迎合而默认接受"。以下三条我**主动提出与用户设计不同的意见**，并附反例。

### 争议一：把"调度决定权"从 Hermes 拆给 Sidecar

**用户的设计**：Hermes 是唯一中心入口，负责选择执行 Agent。

**我的意见**：Hermes 只能**提案**，Sidecar 有**否决权**。

**反例**：设想用户说"帮我把报告里的数字更新一下"。Hermes 计划派 Pi 去改 `report.md`。**但此刻用户自己刚在编辑器里改着这个文件，而且 Claude Code 正在跑另一条任务，它已经把 `report.md` 标记为 `exclusive` 占用**。Hermes 完全不知道这两件事——它是几分钟前被调起来问"该怎么拆任务"的，之后就再没看到运行时状态。它会把任务派出去，两个进程同时写同一个文件，**用户的编辑丢失**。

**代价**：真正的调度逻辑会分裂在两处（Hermes 的提示词里一份，Sidecar 的规则里一份），需要小心维护一致性；用户也可能觉得"大管家怎么连这个都做不了主"。

**我仍然建议这样做**，因为只有 Sidecar 拿得到全部事实。

### 争议二：阶段3 默认**不给** Pi 派写文件的任务

**用户的倾向**：低成本优先，希望多用 Pi。

**我的意见**：阶段3 只让 Pi 干只读的活，写文件交给 Claude Code 或 Codex；等阶段5 的 Worktree 就位再放开。

**反例**（支持用户的理由）：如果 Pi 干不了写活，"Pi 优先"就成了一句空话，成本优化等于没做。而且 Pi 的 `--tools` 白名单已经能把工具限制住，理论上够用。

**我为什么还是反对**：三件事同时成立——① Pi 官方明确写**没有内置沙箱**（`docs/security.md`）；② 项目目录**当前不是 Git 仓库**（实测 `git rev-parse` 失败），**没有回滚**；③ `--tools` 白名单只是"模型配合"，**不是操作系统层面的禁止**，模型仍可能通过 `bash`（如果给了）或扩展绕过。在这三条同时成立的阶段3，让 Pi 优先去写真实文件，是在用用户的真实数据当赌注。等 Worktree 就位（阶段5），这个反对就自动消失了。

**如果用户坚持**：那就走 §3.4 的做法 B（先 `git init` 并让任务前自动提交），把回滚这条补上。**但请不要在既没有回滚、又没有沙箱的情况下放开写权限。**

### 争议三：成本指标以"一次成功率 + 实测用量"为准，第一版**不做自动比价**

**用户的期望**：看起来希望有一个自动的"哪个便宜用哪个"。

**我的意见**：第一版**不做自动比价**，只做**如实记录 + 人工可见**。

**反例**：不做自动比价，"成本优先"听起来就没落地。

**我为什么仍然建议这样做**：本机**没有任何可靠的单价表**——CC Switch 的 `model-pricing.json` 里 `models` 是**空数组**（实测）。而且用户是通过第三方中转（CC Switch 指向本地代理，Codex 的 `base_url` 是 `http://127.0.0.1:15721/v1`）在用模型，**厂商的公开价格表与用户的实际账单根本不是一回事**。在这种情况下做自动比价，会得出一个**看起来很精确、实际是错的**结论，然后拿这个错误结论去做调度决策——这比不做还危险。

**第一版该做的**：把 §3.2 的 7 个量如实记下来，把"每个成功完成任务的总成本"算出来给用户看。**等积累了几十次真实数据、并且找到可信的价格来源之后，再谈自动比价。**
