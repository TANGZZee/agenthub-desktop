阶段3需要保留并复用阶段2的 Sidecar、协议、进程池和事件机制，不应该推倒重写。

## 3. 已确认的产品方向

### 3.1 Hermes 中心化

Hermes 是用户唯一入口和中心调度者，负责：

- 理解用户目标
- 拆解任务
- 选择执行 Agent
- 决定是否需要独立验证
- 管理调度记录和长期记忆
- 汇总结果
- 在失败、冲突或超预算时升级给用户

原任务书已经确定 Hermes 是 Supervisor。阶段3要实现这个目标，而不是重新讨论是否使用 Hermes 中心化。

### 3.2 Hermes 与 Sidecar 分层

Hermes 负责“判断”，Sidecar 负责“执行约束”。

Sidecar 负责：

- 能力和权限校验
- 进程启动、停止和状态管理
- 成本与使用量统计
- 任务依赖
- 文件冲突保护
- 审计记录
- 限制 Hermes 绕过安全策略

不能让 Hermes 直接获得无边界系统权限。

### 3.3 成本优先原则

默认原则是：

> 优先使用“最便宜且足够胜任”的 Agent，不是永远优先最便宜的 Agent。

最终比较指标应是“每成功完成一个任务的总成本”，而不是只看 token。

至少需要记录：

- 输入、输出 token
- 模型或供应商费用
- 重试次数
- 工具调用次数
- 执行时间
- 人工介入次数
- 一次成功率和返工率

Pi 优先只在满足以下条件时成立：

- 任务边界清楚
- 有自动测试或客观验收
- 可以安全回滚
- 不接触密钥和重要系统配置
- 运行在沙箱或受控目录

## 4. 四个 Agent 的官方能力依据

以下内容来自官方仓库说明，计划书需要再次核实并标注版本或访问日期：

- Hermes Agent：<https://github.com/NousResearch/hermes-agent>
- Pi Agent Harness：<https://github.com/earendil-works/pi>
- Claude Code：<https://github.com/anthropics/claude-code>
- Codex：<https://github.com/openai/codex>

### 4.1 Hermes Agent

官方资料体现的能力：

- 长期记忆
- 技能创建与自改进
- 历史会话检索
- 子 Agent 和并行任务
- 定时任务
- Telegram、Discord、Slack、CLI 等入口
- 多个终端和沙箱后端
- 可使用不同模型供应商

建议定位：

> Hermes：总控、长期记忆、调度和最终汇总。

### 4.2 Pi Agent Harness

官方资料体现的能力：

- 轻量终端编程 Agent
- 多模型供应商
- TypeScript 扩展
- Skills
- 会话树、恢复、分支和压缩
- SDK
- JSON/stdio RPC

官方明确说明：

- Pi 没有完整的内置权限隔离系统
- 默认继承启动用户的文件和进程权限
- 需要容器或外部沙箱加强边界

建议定位：

> Pi：低成本首选执行者和可扩展工作台。

需要特别核对：

- 开源 Pi 是编程 Agent Harness，不是 Inflection 的聊天助手 Pi
- “数据分析”应是 Skill 或工具能力，不能仅凭名字写成 Pi 的固有身份
- 如果项目实际接的是另一种自研 Pi Agent，必须单独列出证据并修改定位

### 4.3 Claude Code

官方资料体现的能力：

- 终端、IDE 和 GitHub 中的编程 Agent
- 理解代码库
- 自然语言代码修改
- Git 工作流
- 插件
- Hooks
- MCP
- 自定义 Agents

建议定位：

> Claude Code：复杂代码库、大型重构、架构设计和高风险审查。

### 4.4 Codex

官方资料体现的能力：

- 本地终端编程 Agent
- IDE、桌面和云端形态
- 工程任务执行
- 构建、测试和调试
- 沙箱和审批机制
- Skills 和 AGENTS.md

建议定位：

> Codex：本地工程执行、构建测试、复杂调试、并行实现和独立验证。

注意：

- 四个 Agent 都能处理部分相同的编程任务
- “任务类型相同”不等于“结果质量、权限、成本和失败率相同”
- 调度必须基于能力、风险、成本和实测结果

## 6. Codex 审核时必须检查的问题

### 6.1 事实

- Agent 定位是否有官方依据
- Pi 的身份是否被正确区分
- 哪些是产品要求，哪些是官方能力，哪些只是推测
- 是否把 CC Switch 的能力说得超过实际边界

### 6.2 分层

- Hermes 是否只是判断层
- Sidecar 是否真正掌握执行约束
- Hermes 是否能绕过 Sidecar
- Rust 是否仍然只做进程和事件转发

### 6.3 调度

- 是否存在明确的任务分类
- 是否按能力、权限、成本、风险和健康状态筛选
- 是否记录选择理由
- 是否有手动覆盖
- 是否会重复启动、重复修改或重复验收

### 6.4 成本

- 是否把 token 当成唯一成本
- 是否统计成功任务的完整成本
- 是否包含重试和人工介入
- 是否使用无法获得的数据做精确计算
- 是否给预算设置明确上限

### 6.5 并发与失败

- 多任务并行是否会争抢同一文件
- Sidecar 重启后任务如何恢复
- Agent 崩溃后如何收敛
- 取消和终止是否会误伤其他 Agent
- 旧结果是否会覆盖新结果

### 6.6 安全

- Pi 是否运行在受控目录或沙箱
- 密钥是否被隔离
- 危险命令是否由外层策略阻止
- Agent 是否能自己批准高风险操作
- 审计记录是否足以还原一次调度

### 6.7 验收

- 每一步是否足够小
- 是否有可机测判据
- 是否包含失败路径测试
- 是否包含刷新、重启和并发回归
- 是否与阶段2现有行为兼容

## 7. Codex 审核输出格式

Codex 审核后必须输出：

1. 总体结论：通过 / 有条件通过 / 不通过
2. 问题清单：按严重程度排序
3. 事实与假设核对
4. 进入编码前必须修改的问题
5. 建议修改的问题
6. 实施顺序是否合理
7. 缺失的验收测试

审核完成后停止，不直接编码，等待用户确认。
